# 操作系统考研讲义 03：同步、互斥与 PV 操作

## 同步与互斥怎么区分
互斥解决“共享资源一次只能由一个执行者使用”，同步解决“操作之间必须满足先后关系”。访问临界资源的代码称为临界区。正确方案应考虑互斥、系统推进和有限等待。题目中的“让权等待”强调等待时是否让出处理机，不能把忙等锁都当成阻塞锁。

## 信号量 P、V 操作
本讲义采用允许负值的阻塞信号量定义：P(S) 原子地将 S 减 1，若结果小于 0 则阻塞调用者；V(S) 原子地将 S 加 1，若结果小于等于 0 则唤醒一个等待者。S 小于 0 时，绝对值表示等待者数量。这一负值解释不能直接套到所有实际 API 上。互斥信号量通常初值为 1；表示“尚未发生”的事件信号量常初值为 0。

## 自编同步设计示例：先写后读
共享缓冲区只写入一次，读操作必须在写完成之后开始。设置 ready=0。写进程先写数据，再 V(ready)；读进程先 P(ready)，成功后再读取。此时 ready 表达的是先后关系，不是对所有共享访问的通用互斥锁。

## 有界缓冲区生产者—消费者
设缓冲区容量为 N，empty=N 表示空槽数量，full=0 表示已放入产品数量，mutex=1 保护缓冲区结构。以下是抽象 PV 伪代码，不是可直接运行的 Python。

```text
生产者循环：
    在临界区外生产产品
    P(empty)
    P(mutex)
    将产品放入缓冲区
    V(mutex)
    V(full)

消费者循环：
    P(full)
    P(mutex)
    从缓冲区取出产品
    V(mutex)
    V(empty)
    在临界区外消费产品
```

## 为什么要先申请 empty/full，再申请 mutex
自编反例：缓冲区已满，生产者先 P(mutex) 获得互斥锁，再 P(empty) 被阻塞。消费者想取产品以释放空槽，却必须先取得生产者持有的 mutex，因而也阻塞。生产者等空槽、消费者等锁，系统无法推进。故等待资源数量的 P 操作应放在可能需要由对方获取的互斥锁之外。

## 管程与条件变量
管程把共享数据及其操作封装在一起，并提供互斥进入机制。条件变量用于等待条件，不能当作可累计资源数量的信号量。常见 Mesa 风格下，线程被唤醒后仍需重新获得锁并重新检查条件，所以等待一般写在 while 循环中。

## 做 PV 题的步骤
先列出共享资源与容量，再画先后关系；为每种约束选择信号量并写初值；最后分别检查空、满、并发到达等边界场景，以及是否持锁等待别人释放资源。
